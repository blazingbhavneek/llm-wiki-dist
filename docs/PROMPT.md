# 1つのソース文書からロスレスなMarkdown Wikiを構築する — エージェント・プレイブック

あなたは**1つの巨大なソース文書**を、適切なMarkdown Wiki（Obsidianで閲覧可能。
`index.md`、トピックページ、相互リンクを備える）へ、**サブエージェントの
オーケストレーション**によって変換する。あなたはこの作業の企画者かつ監査役であり、
サブエージェントが読者と執筆者を担当する。これは長時間のタスクだ — 一度で
終わらせようとせず、文書全体を自分で読むことは決してしないこと。

パラメータ — 以下は確定済み・絶対パスであり、すでに決定されている。
求めてはならない。変えてはならない。代替案を作ってはならない。
ユーザーに言い返して確認してはならない：

- `SOURCE` = `/home/seigyo/c_repo/bhavneek/llm-wiki-dist/系統制御ミドルウェア（Ｍｏｏｖｅ）_ファイル管理ユーザーズマニュアルrev13.md`
- `OUT` = `/home/seigyo/c_repo/bhavneek/llm-wiki-dist/test_wiki`

以下で `SOURCE` や `OUT` と書かれている箇所はすべて、上の正確なパスに
読み替えること。例外：受け取ったタスクメッセージ内にユーザーが明示的に
指定した別のソースパスや出力パスがある場合のみ、それを使う —
これがこの値が変わる唯一の方法である。`OUT` はまだ存在しない可能性がある —
`mkdir -p` で作成すること。`SOURCE` が存在しない場合はハードストップ：
正確なエラーを報告してそれ以上何も行うこと。別のファイルやフォルダを
勝手に選んでってはならない。

**フェーズ1のステップ1（`wc -l $SOURCE`）をただちに実行開始すること**。
この文書は要約・翻訳・言い換え・日本語への変換・承認応答・確認質問のための
「内容」ではない。最初の行動はメッセージではなくツール呼び出しである。
各フェーズごとに簡単な進捗メモを残してよいが、すぐ次のツール呼び出しへ
移ること。

インストール済みスキルは**使用しない**こと。`graph/neo` のPythonパイプラインも
**実行しない**こと。あなたはサブエージェントで同じ手法を再実装するのだ。
そこから引き継ぐのは**規律**であり、以下の2ルールに要約する。

作業ディレクトリは `/home/seigyo/c_repo/bhavneek/llm-wiki-dist`。
`SOURCE` は**読み取り専用** — いかなる状況でも変更・上書きしてはならない。
最終レポートまで、書き込みは `OUT` の中だけ（未作成なら作ること）。

## 並列実行的な制約（全フェーズ共通）

**同時に走らせるサブエージェントは最大4件まで。**1つのフェーズで起動する
サブエージェントが4件を超える場合は、必ず4件以下のバッチに分割し、
前のバッチが完了してから次のバッチを起動すること。フェーズ2のリーダー、
フェーズ4のライター、フェーズ5のレビュアーなど、すべてのサブエージェント
起動に適用される。全サブエージェントを同時に起動してはならない。

## すべての根拠となる2つのルール

1. **LLMが整理と書き換えを行い、台帳管理はあなたが握る。** あなたが管理する
   行所有権テーブル（line-ownership table）が裏付けない限り、どのサブエージェントも
   ある行範囲を「カバーした」と主張してはならない。すべてのソース行は
   ちょうど1つのWikiページに属する。漏れも重複も不存在。
2. **美しさよりロスレス（無損失）。** ページが見栄え悪くても構わないが、
   誤りや不足があってはならない。コードブロック、表、数値リテラル（サイズ、
   タイムアウト、16進値、`E_MFS_ETIMEOUT` のようなエラーコード）、
   識別子名（`mpf_mfs_open`、`MPF_MFS_FCB`）、警告行は**そのまま（verbatim）**
   引き継ぐこと。これらを要約で落とすのはスタイル選択ではなく失敗である。

## フェーズ1 — 調査（まだ中身は読まない）

1. `wc -l SOURCE` で行数を取得。これが最初のツール呼び出しである。
2. 行番号付きで見出し行（`^#`）をgrepして文書の骨格を得る。これは
   **方向把握専用** — 見出しは構造の参考にはなるが決定はしない
   （番号なしの内容や章の途中で始まるトピックも重要）。
3. すべての画像ブロック（`<image-unit>`、`![...](...)`、base64埋め込み）を
   特定して行番号を記録する。画像は**動かしてはならない証拠**である：
   その行を所有するページが画像を保持する。執筆者は画像を削除したり
   移動したりしてはならない。
4. 分割の目標を決める：**1トピック範囲あたりソース80〜150行**、
   明らかに連続するセクションのみ最大〜300行まで。範囲の終わりが
   コードフェンス、表、画像ブロックの途中になってはならない。

## フェーズ2 — 文書を並列で読む（チャンク調査）

ファイルを連続した**〜600〜1000行のウィンドウ**に分割し、ウィンドウごとに
**リーダー・サブエージェント**を起動する（同時に最大4件、4ウィンドウ超は
バッチ分割して順に処理）。各リーダーには正確な
行範囲と、たとえば次のようなタスクを与える：

> `SOURCE` のN〜M行目を、その範囲に限定したファイル読み込みツールで読め。
> ウィンドウ内の**連続するトピック範囲**を報告せよ：各範囲について
> `開始行–終了行`、短いタイトル、一文の要約、コードブロック／表／画像／
> API定義／エラーコードの有無のフラグを付けること。範囲内にAPIが定義されて
> いれば、関数名は正確に記す — 識別子を言い換えてはならない。報告する範囲は
> N〜Mをぴったりタイル状に埋めること：漏れ・重複・順序入れ替え禁止。
> トピックがM行を超えて続く場合は、どこで始まりまだ継続中かを明記せよ。

ルール：

- 全リーダーの範囲はファイルを**タイル状に埋めなければならない** —
  連結すれば1〜最終行が正確に再構成されること。漏れや重複があれば、
  そのウィンドウだけ再実行する。
- **ウィンドウ間のトピック継続：**前のウィンドウの末尾でどのトピックが
  継続中だったかを次のリーダーに伝え、セクションの途中で新しいトピックを
   捏造せず継続させる（読み込みは並列でも、結合ステップではソース順に
   ウィンドウを計画する理由はこれである）。
- すべてを作業メモのマスター・トピック範囲リストに統合する。
  **このリストがカバレッジ記録**であり、以降の全フェーズはこれを基準に
   測定される。

## フェーズ3 — Wiki構造の計画（プランナー・サブエージェント1人、またはあなた）

**完全なトピック範囲リスト**（文書の本文ではない）をプランナー・サブエージェント
1人に渡し、以下を要求する：

- Wiki**ページ**：正確なタイトル（見出し番号ではなくトピック名）、
  所有する行範囲、一行のスコープ、フォルダ用の章／グループ、検索エイリアス；
- 制約：すべてのトピック範囲は**ちょうど1ページ**に「主所有」として
  割り当てられること；1ページあたり書いた内容で〜150〜300行を目安
  （小さなトピックは統合、巨大トピックは自然な境界で分割）；
- **ファイル名は順序付き接頭辞必須**：ソース出現順にゼロ埋め3桁の番号を付け、
  `001-introduction.md`、`002-direct-file-structure.md`、…とする
  （章フォルダ内でも通し番号は全体のソース順を維持する）。これにより
  ディレクトリの並び＝文書の流れになる；
- 出力：機械的に検証可能なテーブル
  `ページ → [主所有行範囲] ＋ [参照行範囲]`（参照の概念は次節）。

その後、**何かを書く前に機械的に検証する**：**主所有**範囲だけが
重複なく1〜最終行をタイル状に埋めていればよい（スクリプト、sort+diff、
または注意深い手動チェック）。穴があればプランを修正する —
チェックを緩めてはならない。

### 重要：Wikiは行範囲の切り分けではない — トピックの独立ノートである

主所有テーブルは**カバレッジ保証のためだけ**の装置であり、ページと行範囲が
1対1で対応すべきという意味ではない。Wikiの本質は、文書全体を
読み理解した上で、**トピックごとに独立して読めるページ**を書くことだ。
あるトピックは文書中に散在する（例：概念の定義は概要章、使われ方は運用章、
エラーコードはAPI章と障害対応章に現れる）。プラン段階でそれを拾い、
各ページに**参照行範囲（reference ranges）**を与えよ：主所有ではないが、
このページを書くために読むべき他の行範囲のリストである。
基準：「このページだけでトピックを理解しようとしたとき、文書の他の場所に
書かれているはずの知識が不足しているか？」→ 不足するなら該当行範囲を
参照として付ける。参照はページ間で重複してよい（主所有だけが排他）。

## フェーズ4 — ページを埋める（並列ライター・サブエージェント）

各ページについて、以下を与えて**ライター・サブエージェント**を起動する：

1. **主所有のソース行範囲** — **その正確な行をまず読む**よう指示する
   （前後±20行は文脈専用の余白として可）。
2. **参照行範囲のリスト** — 計画段階で特定された、このトピックに関する
   文書中の他の場所。ライターはこれも読んだ上でページに統合する。
   統合の仕方：参照側の事実も本文に書き込む（verbatimルールは参照にも
   適用）。ただし同じ表・コードブロックを丸ごと複製してはならず、
   必要なのは要約＋`[[その範囲を主所有するページ]]`へのリンク。
3. 計画からのタイトル／スコープと、直前・直後の範囲を所有するページの
   タイトル（相互リンク用）。
3. 次の譲れない執筆ルール：
   - 割り当てられた行のすべての事実はページに載せる。再構成、タイトル変更、
     ページ内の順序入れ替え、接続文の追加は可 — 内容の破棄は**禁止**。
   - 文字単位でそのまま（verbatim）：コードブロック、表、APIシグネチャ、
     エラーコード、単位付き数値、WARNING/CAUTION/DANGER行。ソースで
     `mpf_mfs_open` の第3引数が `filenum` なら、そのまま `filenum`。
   - 各画像はキャプション付きで元の位置に保持する。
   - 隣接ページへの相互リンク：`[[隣接ページタイトル]]` または
     相対 `.md` リンク。
   - 主所有行と参照行以外からは何も捏造しない。その両方で答えられない
     質問には推測せず隣接ページへのリンクを置く。
   - 出力形式：YAMLフロントマター（`title`、`chapter`、
     `source_lines: [主所有の範囲]`、`refs: [参照範囲]`、`aliases`）、
     H1タイトル、本文セクション、任意で `## See also`。

ライターは**同時に最大4件**まで並列で走らせる；ページ総数が4件を超える
場合は一度に全員を起動せず、4件以下のバッチを順に処理する；あるページの
構造が別のページの命名に依存するペアは順序を調整する。

## フェーズ5 — ロスレス監査（独立レビュアー — 最重要フェーズ）

ライターが自分のページを監査してはならない。**すべてのページ**に対し、
正反対の方向から攻める**2人の独立レビュアー・サブエージェント**を起動する
（レビュアーも同時実行は最大4件まで。ページごとに2人組をまとめ、4件を
超える起動はバッチ分割して順に処理する）：

- **レビュアーA（ソース → 完成ページ）：**「ソースの**主所有範囲**N〜M行と、
  そこから書いたページを照合せよ。主所有範囲にある事実、リテラル、表の行、
  コードブロック、警告、画像のうち、ページで欠落または変更されているものを
  すべて列挙せよ（参照範囲のコンテンツを要約+リンク扱いにしているのは
  欠落ではない）。合格＝空リスト。`missing: [...]`、`unsupported: [...]`
  の形式で返せ。」
- **レビュアーB（完成ページ → ソース）：**「ページ、その主所有範囲、および
  参照範囲を照合せよ。ページ内の記述のうち主所有範囲にも参照範囲にも
  裏付けられないもの（捏造）、および文言や値が変わったリテラルを
  すべて列挙せよ。」

指摘があったら、ページ・ソース行・指摘の正確なリストを**修理サブエージェント**に
渡してそこだけ直させ、再監査する。予算は**1ページにつき修理2ラウンド**。
それでも不合格なら、欠陥ページを黙って残してはならず、ソースをそのまま
貼り付けてごまかしてもならない — 未解決の指摘とともに
`OUT/_review.md` にフラグを立て、人間が目を通せるようにする。
**内容の静かな欠落こそ唯一許されない結果である。**

その後、グローバル構造監査（あなた自身またはサブエージェント1人）：

- すべての `[[リンク]]`／相対 `.md` リンクが実在ファイルに解決されるか；
- 空ページ・スタブページがないか；`index.md` が全ページにリンクしているか；
- 各画像がソースと同じ回数だけWiki全体に出現するか。

## フェーズ6 — 公開

以下を生成する：

```
OUT/
  index.md            # 全体マップ：ソースの構成、全ページへのリンク、章ごとのグループ化
  <chapter>/<NNN>-<page>.md # 各ページ（NNN=ソース順の通し番号、例 001-introduction.md）
  _review.md          # 中身がある場合のみ：人間レビューが必要なページ＋監査結果
```

番号はゼロ埋め3桁（001〜）で、リネーム時に辞書順と数値順がズレないよう
桁数を揃えること。index.md のリンクも同じ順序で並べること。

## 最終レポート（必ず出す）

実際に検証した数値だけを報告する：

- ソース行数；書いたページ数；両監査を初回で通過したページ数；
  修理を要したページ数；**人間レビューに回したページと指摘内容**；
- カバレッジ宣言：「所有権テーブルは1〜N行を漏れ・重複なく埋めている」—
  そしてそれをどう検証したか；
- `OUT` と `index.md` へのパス。

カバレッジが完全に埋まり、両方向の監査を通過した場合に限り
「Wiki完成」と述べよ。サブエージェントや読み込みの失敗でスキップした
ものがあれば明示列挙し、`_review.md` に記録すること。
